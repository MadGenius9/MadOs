# CLAUDE.md — working on MadOS

Read this first. Then read `docs/architecture/overview.md` and the ADRs it
links before changing architecture.

## What MadOS is

A real, bootable x86_64 UEFI desktop operating system (working codename
"MadOS", version in `product/product.toml`). **Not** a web app, Electron
desktop, mockup or simulation. 0.1 = Fedora 44 Kinoite (KDE Plasma, bootc/
OSTree) as base + MadOS-owned services and apps on top:

- `crates/mados-core` — product metadata, real system info, logging, names
- `crates/mados-api` — D-Bus contracts (`org.mados.System1`, `org.mados.Assistant1`)
- `services/mados-daemon` — root system service; polkit-checked actions
- `services/mados-ai` — user assistant; text → `Intent` → policy → APIs
- `apps/mados-settings` — GTK 4 settings app (includes About)
- `apps/madosctl` — CLI; also emits boot markers for smoke tests
- `image/` — Containerfile (bootc), `config.env`, `installer/` (ISO)
- `system/` — files installed into the image (`rootfs/`, `templates/`, `variants/dev/`)
- `scripts/` — build tooling; `tests/config`, `tests/smoke` — validation and VM tests

## Current milestone

M1 (bootable VM image) is implemented but its image build/boot has not yet
been verified: the bootstrap environment blocks Fedora's servers. The CI
`image` job is the reference build. See `docs/roadmap.md` for status.

## Commands

```sh
make setup            # prerequisite check (never installs)
make build            # cargo build --workspace --locked
make test             # fmt + clippy -D warnings + cargo test + config validation + VM harness self-test
make test-unit | test-lint | test-config | test-harness
sh scripts/repro-check.sh
make image disk iso   # need root podman + network access to quay.io/Fedora/ghcr.io
make vm | vm-iso | smoke
python3 scripts/product.py get product.name   # product values for shell code
```

## Rules

### Verify, don't claim
- Never say something works unless you ran it and it passed. Otherwise say
  "implemented, unverified" and why (e.g. no network to Fedora, no KVM).
- Run `make test` before committing. Run `make image disk smoke` when the
  environment allows; report the exact failure point when it doesn't.
- Update `README.md` status tables and `docs/roadmap.md` when status changes.

### Architecture
- Record architectural decisions as ADRs in `docs/architecture/` and update
  `overview.md` when components, interfaces or boundaries change.
- GUIs and the assistant change system state only via D-Bus methods of the
  owning service. **No shell commands from apps.** Services exec only fixed
  absolute paths with fixed arguments.
- Privileged methods authorize the **calling** D-Bus peer with polkit; add a
  polkit action for each new privileged capability.
- The assistant may only produce variants of the closed `Intent` enum. Never
  add an intent that executes arbitrary commands, files or scripts. Every
  state change requires user confirmation. New capability = Intent variant +
  policy row + executor arm + tests.
- Don't reimplement mature upstream infrastructure (kernel, NetworkManager,
  PipeWire, systemd…). Don't describe upstream components as MadOS technology.
- Don't create empty directories for future components.

### Branding and versioning
- Product name, version, vendor, URLs, logo and accent live **only** in
  `product/product.toml` (+ `product/assets/`). Rust reads them through
  `mados_core::Product`; shell through `scripts/product.py`; image files are
  generated by `scripts/stage-system.py`. `tests/config/validate.py` fails on
  hard-coded product names in code strings, `system/` or `image/`.
- Technical identifiers (`org.mados.*`, `/usr/lib/mados`, crate names) are
  stable API; don't rename them casually.
- Crate versions in Cargo.toml are not the product version.

### Code style
- Rust 2021, `cargo fmt` (max width 120), clippy clean with `-D warnings`.
- Services log via `mados_core::log_*` macros (journald priorities); log
  state changes and failures, not routine reads.
- Wire formats: JSON with a `schema` field.
- Blocking work in GTK code goes through `bg::run`.
- Shell: POSIX `sh`, shellcheck clean. Python: stdlib only, ≥ 3.11.
- Match the surrounding code's comment density and idioms.

### Security — never
- Never commit or bake in passwords, API keys, tokens or private keys.
- Never disable SELinux, Secure Boot compatibility or service hardening to
  make something work without an ADR and a prominent note in `docs/security.md`.
- Never give mados-ai root, a shell, or generic D-Bus passthrough.
- Dev-only conveniences (autologin, serial console) must stay in the `dev`
  variant; validation enforces this.

### Host safety — never
- Never modify the developer's host: partitions, EFI system partition,
  bootloader, Secure Boot settings, disk layout.
- Never run `dd`, `wipefs`, `mkfs`, `fdisk`, `parted` (or similar) against
  real block devices. Destructive operations target only image files under
  `out/` or explicitly configured virtual disks.
- Testing is VM-only. Physical installation is milestone M8 and needs its own
  explicit plan and approval.
- Don't silently install host packages; `make setup` reports, the developer
  installs. Image steps announce before using `sudo`.

## Supported platform

x86_64, UEFI, QEMU/KVM (q35 + OVMF) for now. Modern Intel/AMD laptops are the
eventual target (M8). See `docs/hardware/support.md`.
